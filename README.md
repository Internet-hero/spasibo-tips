# «Спасибо» — онлайн-чаевые по QR на чеке

Демо по кейсу «Онлайн-чаевые: платформа для ресторанов» для сети «Вкус-Сервис». React + TypeScript + Vite, исходные CSV, localStorage и детерминированный эмулятор шлюза. Backend и реальные платежи отсутствуют.

Для передачи проекта другой нейросети используйте [AI_HANDOFF.md](AI_HANDOFF.md): там собраны архитектура, сценарии, ограничения, команды проверки и готовый контекстный запрос.

## Запуск

```bash
npm install
npm run dev
```

Production-сборка: `npm run build`; локальная проверка сборки: `npm run preview`.

Материалы командной сдачи находятся в `case_3_tips/`: заполненные документы ТЗ, CSV, CLI-прототип, draw.io-схемы, журнал промптов и контрольные артефакты. Рабочая ветка — `team_case_3`.

## Демо-сценарии

- Гостевой чек: `/pay?qr=qr_001` (старый адрес `/p/qr_001` также поддерживается); сумма 637,00 ₽, быстрый выбор 10% или 15%, произвольная неотрицательная сумма чаевых с лимитом 50% по ТЗ. При превышении автоматически устанавливается 50%, а после успешной оплаты открывается форма отзыва — он сохраняется в платеже и виден сотруднику в кабинете. После отказа шлюза QR не сгорает: на экране статуса есть «Попробовать снова».
- `qr_001` всегда демонстрирует `SUCCESS`; `qr_003` — `DECLINED / CARD_DECLINED`; для остальных QR используется hash-формула из ТЗ.
- Для отмены `CREATED` откройте `/p/qr_002`, перейдите к подтверждению и нажмите «Отменить платёж».
- Вход в кабинеты официанта, мерчанта и администратора: любые непустые логин и пароль. Это только визуальная авторизация.
- Приглашение официанта: `ANNA2026`.
- Мерчант регистрируется со статусом `PENDING`; активировать его может администратор.
- QR создаётся на конкретный `receipt_id`, содержит 6 обязательных полей payload, HMAC-SHA256, nonce и TTL 24 часа.

## Данные и безопасность

Исходные файлы `merchants.csv`, `employees.csv`, `payments.csv`, `qr_links.csv` находятся в `src/data/` и не изменены. Для демонстрационных платежей Вероники используются увеличенные суммы чаевых 250 ₽ и 450 ₽. В localStorage используется ключ `spasibo-demo-state-v3`.

Реализованы идемпотентность, одноразовый nonce, привязка к чеку, пять статусов платежа, отчёты по мерчанту/официанту/дням с `report_id`, CSV-выгрузка, отзывы в платеже и аудит из 9 полей. QR считается использованным только после успешной оплаты, поэтому отказ и отмена оставляют возможность повторить попытку. Реквизиты сотрудников хранятся только как `****NNNN`; PAN и CVV клиентов не запрашиваются.

Это статическое хакатон-демо. Демонстрационный HMAC-секрет находится в клиентском коде только для воспроизведения ТЗ; production-версии нужны серверная проверка подписи, защищённое хранилище ключей, API и настоящая RBAC-авторизация.

## Соответствие API из ТЗ

Бэкенда в демо нет, но операции названы и разделены так же, как в `case_3_tips/05_api_schemas.yaml`:

| Endpoint из ТЗ | В демо |
|---|---|
| `GET /api/v1/qr/{qr_id}` | экран `/p/:qrId` и `/pay?qr=…`, проверка в `validateQr` |
| `POST /api/v1/tips` | `demoActions.createPayment` (идемпотентность по `idempotency_key`) |
| `POST /api/v1/payments/{id}/confirm` | `demoActions.confirmPayment` → `PENDING` и результат эмулятора |
| `POST /api/v1/payments/{id}/cancel` | `demoActions.cancelPayment` (только из `CREATED`) |
| `GET /api/v1/reports/tips` | `merchantReport` / `employeeReport` и экран `/#/manager` с `report_id` |

Коды ошибок и HTTP-статусы совпадают с таблицей из приложения (`INVALID_QR` 422, `QR_EXPIRED` 410,
`QR_USED` 409, `MERCHANT_BLOCKED` 403, `CANCEL_NOT_ALLOWED` 409, `RATE_LIMITED` 429).
